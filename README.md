# AI Services Explained

GitHub repository: https://github.com/yves-schillings/ai-services-explained

Commented Python examples for the Secloudis article *AI Services Explained*.
All code in this repository is written by **Yves Schillings**.

Everything uses **fictional data** generated by the code. No real organisation,
case or person appears. The examples never download model weights, except the
one-server stack test, which pulls two small open models into a Docker volume
(never into this repository).

## Contents

All examples are in `examples/`:

- **Training examples (01, 02 and 13 to 17).** Each one trains a model, evaluates it
  on separate data and writes its measured results to `results/`. The article and its
  slides show exact excerpts of these files and link to the lines they quote.
- **Release and serving (19 and 18).** The release step checks the agreed gate and
  records a named owner's decision. The FastAPI service loads only the approved version.
- **Service examples (03 to 12).** Short inference, retrieval, agent, OCR and speech
  examples. Several need a local model server or engine. Their tests check the
  application controls with mocked model calls. They do not measure model quality.

Shared helpers:

- `fictional_data.py` generates the fictional documents, the fixed final test set,
  the splits and the run evidence (versions, threads, code revision).
- `page_images.py` draws the fictional page images.
- `mlflow_tracking.py` points MLflow at a local store (or at a tracking server).
- `release_records.py` reads and appends the approval record.

`deploy/one-server/` runs a model server, MLflow, PostgreSQL with pgvector and the
application on one GPU machine with Docker Compose. It was tested end to end.

## Run the training examples

Python 3.12, CPU only. Install the exact versions, then run from the repository root:

```powershell
python -m pip install -r requirements.txt
python examples/01_machine_learning.py        # classification, baselines, leakage, MLflow runs and versions
python examples/19_model_release.py           # the gate and a named owner decide; rollback drill
python examples/18_model_serving.py           # serves the approved version on 127.0.0.1:8800
python examples/02_deep_learning.py           # MLP and CNN training loop, adaptation over 5 seeds
python examples/13_regression.py              # regression, underfitting and overfitting
python examples/14_clustering.py              # clustering with dimensionality reduction
python examples/15_anomaly_detection.py       # anomaly detection
python examples/16_time_series_forecast.py    # time series with a temporal split
python examples/17_autoencoder.py             # autoencoder for unusual pages
python -m pytest tests -q
```

Roll back the live version:

```powershell
python examples/19_model_release.py --rollback "reason"
```

## MLflow: what it keeps and what it does not decide

Examples 01 and 02 record every training run in MLflow:

- parameters, the data version and the fixed test set version,
- metrics, and curves logged step by step (the validation curve over C, the loss and
  accuracy per epoch),
- the saved model with its exact dependencies (`requirements.txt` beside the model),
- a new version in the MLflow Model Registry (`document-triage`, `page-layout-cnn`).

An **experiment** groups the runs of one task. A **run** is one training execution with
its parameters, metrics and files. A **registered model version** is a numbered model
in the registry, linked to the run that produced it.

Browse and compare the runs:

```powershell
mlflow ui --backend-store-uri sqlite:///mlflow/mlflow.db
```

Two screenshots of that interface come from the runs in `results/`:

- `results/mlflow_compare_runs.png` compares the three document-triage runs (100, 200
  and 400 labelled cases) metric by metric. On the same final test set, macro-F1 rises
  from 0.82 to 0.89 and 0.92, the validation curves over C show where the small pool
  falls behind, and the share sent to review rises with the largest pool.
- `results/mlflow_training_curves.png` shows the training and validation loss per epoch
  of the MLP and CNN runs, and their test accuracy. The CNN stops early at epoch 13.

The screenshots crop out MLflow's assistant side panel and keep only the run data.

**MLflow keeps the information. It does not authorise go-live.** The release step
(`19_model_release.py`) checks the gate in code and records a named owner's decision in
an approval record kept apart from the model files (`approvals/`, or
`TRIAGE_APPROVALS_DIR`). Only then does it point the MLflow alias `live` at the version,
for information. The service (`18_model_serving.py`) trusts the approval record, not the
alias. It refuses:

- a version that is pending, denied or withdrawn,
- a version whose recorded test score is below the gate,
- model files whose digest differs from the approved digest, including files replaced
  together with their MLflow metadata. A checksum proves integrity only against a
  reference that is protected on its own, which is why the reference lives in the
  approval record.

Rollback: the owner withdraws the live version, and the service serves the previous
approved version at its next start. Saved scikit-learn models use MLflow's default
`skops` format, and the CNN is saved as a traced graph (`pt2`). Neither needs the
training script to be loaded.

The local example uses fictional owners and trusted release commands. Training and
release share the jobs container. Production needs authenticated approvers, separate
training and release identities, restricted approval-store writers and protected audit
storage. The application's approval volume is mounted read-only in the tested stack.

## Reproducibility

- `requirements.txt` pins the exact versions used. The CPU build of torch is the default
  on Windows. On Linux, install it from `https://download.pytorch.org/whl/cpu`.
- Seeds are fixed in the code. Example 02 fixes 4 CPU threads and requests deterministic
  algorithms: another thread count can change the neural-network results.
- Every results file records the command, the Python and package versions, the thread
  count and the code revision (`environment`).
- A clean virtual environment installed from `requirements.txt` passes the tests.

## What each training example teaches

- **01**: the full lifecycle. Need and acceptance criterion, a fixed final test set,
  split by case, hyperparameters chosen on validation, one final test, baselines,
  uncertainty, the cost of review and errors, leakage, MLflow runs and versions,
  inference from the registry, and monitoring after release.
- **02**: forward pass, loss, backpropagation, optimiser step, batch, epoch, learning
  rate, early stopping, and which weights learn in each adaptation mode.
- **13**: regression and the difference between underfitting and overfitting.
- **14**: unsupervised grouping and dimensionality reduction with TruncatedSVD.
- **15**: unsupervised anomaly scores. An anomaly is never evidence of wrongdoing.
- **16**: why a time series needs a temporal split, and a leaky centred average.
- **17**: learning a representation without labels.
- **18 and 19**: go-live decided by a gate and a named owner, served only after checks,
  and rolled back by withdrawing the live version.

## Service examples

03 local language inference, 04 controlled draft generation, 05 permitted semantic
retrieval and generation, 06 bounded tool use, 07 OCR, 08 transcription,
09 multimodal interpretation, 10 embeddings, 11 translation and 12 elementary redaction.
Examples 03 to 06 and 09 to 11 need a model already installed in a local Ollama
server. The HTTP client is fixed to 127.0.0.1 and disables inherited proxies. This
does not establish the security or offline configuration of that server.
Speech needs faster-whisper (`requirements-speech.txt`) with local model files. OCR
needs the Tesseract executable and its language data on PATH.

## One server

`deploy/one-server/` puts the model server (Ollama), the MLflow tracking server,
PostgreSQL (MLflow metadata, plus pgvector for retrieval), the model files and the
application on one GPU machine. Its README records the end-to-end test: commands,
outputs and timings. Four points matter when reading it:

- Containers isolate processes. The separation between projects still has to be
  configured: networks, volumes, database users and resource limits.
- Versions and rollback work on one server with the MLflow registry, an approval
  record and a deployment procedure. KServe is not required for that.
- Docker Compose assigns GPUs per container. Here only the model server receives the GPU.
- One server stays a single point of failure. Installing Kubernetes on that one machine
  does not remove it.

MLflow is not needed just to call a pretrained LLM. It earns its place for experiments,
evaluations and model versions.

## Cloud training (prepared)

`cloud/` trains the same document classifier and page network outside the laptop, with the
same fictional data, split, metrics and gate. Everything there is **prepared, not executed**:
the code and configuration are checked by offline tests, and no cloud resource was created.

- `cloud/azure/`: an Azure Machine Learning command job, MLflow tracking in the workspace,
  model registration, a managed online endpoint and a client call.
- `cloud/aws/sagemaker/`: a SageMaker AI training job with the same script, managed MLflow
  tracking, the model in S3 and a real-time endpoint.
- `cloud/aws/bedrock/`: a Bedrock fine-tuning job for a supported foundation model, with a
  before and after evaluation and prompt-injection tests. This path does not run your own
  scikit-learn or PyTorch code, and no weight download is documented.
- `cloud/README.md`: the data sent and its destination, the cost elements, what ran and what
  is prepared, and how to get each trained model back for local hosting.

```powershell
python -m pytest cloud/tests -q
```

Running a cloud example needs an account owner, a budget and approval of the data sent.

## Verification

`python -m pytest tests -q` runs the deterministic tests:

- `tests/test_training.py` checks the split by case, the fixed final test set outside
  every pool, the vectoriser fitted on training data only, the review threshold,
  forecast features that use only the past, the release gate, every refusal of the
  service (pending, denied, below the gate, tampered file, model swapped with its
  metadata), serving the approved version and rolling back, evaluation that changes no
  weight, and frozen layers that do not change.
- `tests/test_examples.py` checks access filtering, schema refusal, agent tool
  permissions and bounded execution of the service examples, with mocked model or OCR calls.

## Limits

The data is synthetic and small. The scores show how training and evaluation work.
They are not evidence of quality on real documents, recordings or languages.
These are educational applications, not a complete authentication service or
production deployment bundle. Check upstream package and model licences before any deployment.
